# Требования Runforge Runs

## Источник и границы

Требования из PDF задают ожидаемый результат продукта. Упоминания отправки в чат, согласования с HR и размещения демо
фиксируются как условия сдачи для владельца проекта; сами по себе они не разрешают агенту внешнюю отправку или публикацию.

Прямые решения пользователя для этого проекта:

- Сохранить текущую структуру `src/app`, `src/components`, `src/entities`, `src/features`, `src/hooks`, `src/utils`, `agents`.
- Использовать CSS Modules и mock-сервис вместо backend.
- Создать README.MD, корневой AGENTS.MD с переходом в agents/AGENTS.MD и этот REQUIREMENTS.MD.
- По последующему запросу: ESLint и Prettier с отступом в два пробела; понятный интерфейс `useRuns` с `data`, `error`, `status` и вычисляемыми флагами.

Из разрешённых PDF вариантов выбран TypeScript; React + Vite соответствует рекомендованному сочетанию.

## 1. Стек и ограничения — PDF §01–02

| ID      | Требование                                                                | Проверка                                                                                     |
| ------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| TECH-01 | React; Vite рекомендован и выбран для проекта.                            | Приложение запускается через Vite и использует React.                                        |
| TECH-02 | JavaScript или TypeScript; TypeScript является плюсом и выбран здесь.     | Исходники типизированы, проверка типов проходит.                                             |
| TECH-03 | HTML и CSS; по решению пользователя CSS Modules.                          | Стили компонентов в `*.module.css`, глобальные стили ограничены базовыми правилами.          |
| TECH-04 | Локальный mock-сервис, возвращающий Promise с набором запусков.           | UI получает данные через асинхронный сервис; fixtures не подменяют запрос внутри компонента. |
| TECH-05 | Git и README с инструкцией запуска.                                       | Исходники ведутся в Git; чистая установка и запуск воспроизводимы по README.                 |

REST concepts указаны в стеке PDF; реальный HTTP-сервер не требуется. Отделённый контракт сервиса позволяет показать обработку запросов.

## 2. Модель данных

Сохранить исходную модель без переименования полей и значений статуса:

```ts
type RunStatus = 'queued' | 'running' | 'succeeded' | 'failed';

type Run = {
  id: string;
  name: string;
  repository: string;
  branch: string;
  status: RunStatus;
  createdAt: string;
  durationSeconds?: number;
  logs: string[];
  result?: string;
};
```

ISO 8601 для `createdAt` — выбранный формат fixtures, а не дополнительное требование PDF.
Отсутствие `durationSeconds` и `result` допустимо. Значение длительности `0` не считать отсутствующим.

## 3. Обязательная функциональность

| ID      | Требование                                               | Критерий приёмки                                                                                                    |
| ------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| FUNC-01 | Список запусков.                                         | В каждом элементе есть название, репозиторий, ветка, статус, дата создания; длительность показана, если известна.   |
| FUNC-02 | Фильтр статуса: All, Queued, Running, Succeeded, Failed. | Каждый фильтр ограничивает список соответствующим статусом, All показывает все; активный вариант заметен.           |
| FUNC-03 | Поиск по названию запуска или репозиторию.               | Подходящий запуск находится по любому из этих полей; поиск и фильтр статуса применяются одновременно.               |
| FUNC-04 | Подробности по клику на строку или карточку.             | Открывается модальное окно с данными запуска, логами и результатом при его наличии. Есть понятный возврат к списку. |
| FUNC-05 | Визуально различимые статусы.                            | Статус имеет текстовую подпись; значение понятно без различения цветов.                                             |
| FUNC-06 | Состояния данных.                                        | Есть загрузка, ошибка с повтором и пустой результат поиска/фильтра.                                                 |

Для поиска принято регистронезависимое сопоставление подстроки с удалением пробелов по краям запроса.
Это уточнение реализации; PDF не задаёт алгоритм, debounce, серверный поиск или поиск по ветке.

## 4. Состояния и поведение

| ID       | Состояние        | Критерий приёмки                                                                                                                           |
| -------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| STATE-01 | Загрузка         | Пока Promise ожидает ответ, виден индикатор или skeleton. Небольшая задержка делает состояние наблюдаемым; сейчас в сервисе задано 850 мс. |
| STATE-02 | Успех            | После ответа виден список; в готовом задании работают поиск и фильтры.                                                                     |
| STATE-03 | Пустой результат | При отсутствии совпадений понятно, что ничего не найдено; предложен сброс поиска или фильтров.                                             |
| STATE-04 | Ошибка           | Сообщение объясняет сбой, кнопка «Повторить» запускает новый запрос. Ошибку необязательно включать в обычный сценарий.                     |
| STATE-05 | Подробности      | Видны данные выбранного запуска, несколько строк логов и результат, если он задан.                                                         |

Надёжная отмена запросов и защита от устаревшего ответа — решения реализации сервиса/hook, а не самостоятельные пункты PDF.
Ошибки моделируются явно, без случайности, чтобы проверка оставалась воспроизводимой.

Базовые семантические элементы, подписи полей и видимый фокус использовать при разработке.

## 6. Проверочные данные

- Не менее 6 запусков.
- Каждый содержит название, репозиторий, ветку и несколько строк логов, а также остальные обязательные поля модели.
- В наборе присутствуют queued, running, succeeded, failed.
- Для проверки необязательных полей в локальные fixtures дополнительно включены примеры без длительности, без результата и с нулевой длительностью.

Последний пункт — выбранные граничные случаи, а не отдельное требование к набору из PDF.

## 7. Проверки

Три автотеста приветствуются и дают плюс, но не сформулированы как безусловно обязательные:

1. Фильтрация по статусу.
2. Поиск.
3. Открытие подробностей.

PDF предлагает Vitest и React Testing Library. Если этих тестов нет, нужно описать ручную проверку сценариев в README.
Тесты сервиса проверяют инфраструктуру запросов и не засчитываются как реализация этих трёх UI-сценариев.

Сценарии приёмки:

| ID       | Действия                                                       | Ожидаемый результат                                                                   |
| -------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| CHECK-01 | Открыть страницу и дождаться ответа.                           | Видна загрузка, затем не менее 6 запусков, представлены все статусы.                  |
| CHECK-02 | По очереди выбрать каждый статус и All.                        | Список соответствует фильтру, активный вариант заметен.                               |
| CHECK-03 | Найти запуск по части названия, затем по репозиторию.          | В обоих случаях остаются совпадения; выбранное правило поиска не зависит от регистра. |
| CHECK-04 | Выбрать статус и ввести запрос.                                | Отображается пересечение обоих условий; очистка поиска сохраняет статус.              |
| CHECK-05 | Ввести запрос без совпадений и сбросить условия.               | Видно сообщение и действие сброса; после сброса список возвращается.                  |
| CHECK-06 | Открыть запуск, проверить данные, логи и результат, вернуться. | Открыты данные именно выбранного запуска; есть явное действие возврата.               |
| CHECK-07 | Открыть запуск без результата/длительности.                    | Нет пустого сломанного блока или `undefined`, отсутствующая длительность обработана.  |
| CHECK-08 | Вызвать ошибку mock-сервиса и повторить запрос.                | Видны сообщение и кнопка повтора; повтор восстанавливает список.                      |
| CHECK-09 | Проверить экран 360 px и desktop.                              | Контент читаем, элементы доступны, консоль без ошибок.                                |

## 8. AI_LOG и сдача

Обязательная документация для готового задания:

- README с командами установки, запуска и тестов и краткой структурой проекта.
- `AI_LOG.md` в корне, примерно полстраницы: инструмент и модель; 2–3 полезных запроса и переданный контекст; ошибка/неудачное предложение AI и способ обнаружения и исправления.
- Понимание предложенного AI кода и проверка изменений перед сдачей.
- ZIP с исходным кодом проекта, README и AI_LOG; по PDF владелец отправляет его в чат, где получено задание.

Организационные условия PDF: сдача в течение 3 дней с момента получения, ориентир чистого времени 2–3 часа;
до начала HR письменно подтверждает условия оплаты, вопросы направляются в исходный чат.
Дата получения не сообщена, поэтому календарный дедлайн здесь не вычисляется.
Эти условия не являются функциональными требованиями приложения.

## 9. Необязательные бонусы

- Сортировка по дате или длительности запуска.
- Сохранение выбранного фильтра в параметрах URL.
- Размещение демо (например, Vercel) и ссылка в README.
- Дополнительные тесты и улучшенное управление интерфейсом с клавиатуры.

Бонусы не должны подменять выполнение обязательных сценариев. Они пока не реализованы.
